# W9.2D — PlayCanvas + Real CC0 Model Hero Slice

Date: 2026-10-08
Status: DRAFT / CI AND VISUAL REVIEW PENDING

## Decision

The earlier self-written WebGL2 renderer (C) failed visual quality and camera
composition on real Android even after its projection bug was fixed. Do not
extend that shader as a long-term production base. Build a *separate* one-level
PlayCanvas prototype with actual licensed 3D game assets, and decide with
real screenshots and a physical Android test before migrating anything.

## Authentic starter and asset provenance

PlayCanvas Engine startup, camera/light setup and Vite/TypeScript shape follow
the **official PlayCanvas Engine starter**, MIT:
https://github.com/playcanvas/create-playcanvas/tree/main/templates/engine/third-person-controller
https://github.com/playcanvas/create-playcanvas/blob/main/LICENSE

Five **real Kenney CC0 1.0 GLBs** are fetched during CI/build from
https://github.com/Hidencod/tge-assets at commit
`08f0c913f6783cc81f9f6105a7cdda8562b1c192`, based on the original
Kenney asset packs at https://kenney.nl/assets.
Exact source paths and byte sizes are in
`spikes/w9-playcanvas/asset-manifest.json`.

- Animated-by-transform (not skeletal) mini-character
- Grass platform / blocks
- 3D coin
- Oak tree
- Flag

Models are bundled with the HTML5 build in `playtest-dist/3d/models/`.
They are not hotlinked at runtime. Build fails if a pinned model cannot be
fetched or the binary GLB magic/length is invalid. These are existing genuine
3D art assets, not hand-built cubes masquerading as completed models.

The owner's accepted `MassRunnerModel` still owns forward speed, mass
growth, collisions, arithmetic gates, and Level 1 success/fail. Imported
assets and PlayCanvas form an opt-in **visual/interaction presentation slice**,
not a second game engine or a duplicated score source of truth.

## Build / test

```bash
npm install
npm run verify
npm run package:playtest
npm run build:w9-2d
npm run test:w9-2d
```

Standalone entry, after a validated build:
`playtest-dist/3d/index.html`.
CI attaches the entire app and screenshots, including:
390 × 844 portrait, 360 × 800 small Android and 844 × 390 landscape.

Technical acceptance requires no off-origin requests, all five GLBs
loaded, PlayCanvas engine initialized, viewport occupancy, touch steering,
correct mass model and deterministic 1-level phase progression.

**Separate visual acceptance is mandatory.** Inspect the actual screenshots
before publishing; verify player + gates are comfortably visible and neither
HUD nor 3D are squashed into a thin central band. Real Android is required
for FPS, device heat, input feel and art-direction approval. Headless
Chromium passing is insufficient, as demonstrated by the previous C failure.

A/B existing public variants remain unchanged. No PlayCanvas route
may replace the W9 default before approved. New 3D must also preserve
the previous manual-only Pages publishing policy.

## Human review target

- Camera/scene use available mobile viewport.
- Gameplay-critical HUD legibility (16+ px where feasible).
- Character, track and next decisions visually prominent.
- Better color/material richness than prior C prototype.
- Smooth physical Android, no hard-stutter; consider FPS evidence.
- Sound not yet remixed/validated by this isolated visual slice;
  no false claims of complete audiovisual quality.
- The model has a *procedural bounce*, not genuine skeletal-run animation:
  adopting animated CC0 glTF later is an explicit next-step option if
  the visual direction passes.

Outcome: GO for single-level 3D improvement, ITERATE 1–3 high impact defects,
or STOP and revert to tested 2.5D. Avoid broader factory work until then.
